# 이슈 구현

이 스킬은 대개 **새 세션**에서 이슈 하나만 받고 시작한다. 이전 대화 맥락이 없으므로 이슈 본문·댓글·결정 기록과 저장소 문서가 유일한 근거다. 목표는 이슈의 완료 조건을 테스트로 증명하는 PR 하나다.

흐름: **준비 → 분류 → 테스트 → 구현 → 검증 → 이슈 갱신 → PR**

## 1. 준비

1. **이슈 읽기** — `gh issue view <N> -R <repo> --comments`. 다른 저장소 이슈면 `owner/repo#N`.
   - "사용자 검토 필요"에 **열린 항목(`- [ ]`)이 있으면 그 부분은 구현하지 않는다.** 결정이 필요한 이유와 권장안을 정리해 사용자에게 묻는다. 결정과 무관한 부분만 먼저 진행할 수 있으면 그렇게 말하고 진행한다. 이슈는 사용자가 결정한 대로 구현하는 것이 원칙이라, 추측으로 결정을 대신하면 리뷰에서 되돌려진다.
   - "결정 기록"·댓글의 결정이 본문 다른 곳(작업 내용·대상)보다 우선한다 — 결정이 나중에 붙은 경우가 많다.
   - "관련 이슈"에 **선행 이슈**가 있고 아직 열려 있으면 사용자에게 알린다(예: 클라이언트 먼저 배포).
2. **저장소 설정·문서** — `.claude/github-issue.yml`(특히 `verify`), `CLAUDE.md`, `README.md`, `docs/REPO_ARCHITECTURE.md` 가 있으면 읽는다. 저장소 문서가 이 스킬·공통 가이드보다 우선한다.
3. **언어별 공통 가이드** — 바뀔 파일의 언어로 고른다. 이 플러그인의 `docs/<lang>/` 에 있다:
   - 경로: `${CLAUDE_SKILL_DIR}/../../docs/<lang>/CODE_STYLE.md`, 구조는 같은 폴더의 `CLEAN_ARCHITECTURE.md`
   - 언어 판별: `Cargo.toml`·`.rs` → `rust`. 그 밖의 언어는 `ls ${CLAUDE_SKILL_DIR}/../../docs/` 로 있는 폴더를 확인한다.
   - 해당 언어 폴더가 없으면 저장소 문서와 그 언어의 일반 관례를 따르고, PR 의 "참고"에 가이드 없음을 적는다.
4. **브랜치** — 기본 브랜치를 최신으로 받고 `<type>/<id-소문자>-<짧은-이름>`(예: `refactor/order-002-remove-v1-order`) 브랜치를 만든다. 기본 브랜치에 직접 커밋하지 않는다. 작업 트리가 깨끗하지 않으면 시작 전에 사용자에게 알린다.
5. **기준선** — 고치기 전에 `verify` 명령을 한 번 돌려 결과(통과·실패 수)를 적어 둔다. 원래 실패하던 테스트를 내 변경 탓으로 착각하지 않기 위해서다. 실행 환경(Docker 컨테이너 등)은 저장소 README 를 따른다.

## 2. 분류

이슈 라벨·제목·개요로 종류를 정한다. 섞여 있으면 이슈를 나누자고 제안하거나, 커밋을 종류별로 나눈다.

| 종류 | 예 | 테스트 원칙 | 상세 |
|---|---|---|---|
| **신규 기능·버그 수정** | API 추가, 규칙 변경, 버그 | 바뀔 동작을 테스트로 먼저 쓰고 **실패를 확인**한 뒤 구현 | [references/feature.md](references/feature.md) |
| **리팩토링·레거시 제거** | 구조 이동, enum 도입, 경로·컬럼 제거 | 남는 동작은 **그대로**(같은 테스트가 통과), 없애는 동작은 없어졌음을 테스트 | [references/refactor.md](references/refactor.md) |

해당 상세 문서를 읽고 따른다.

## 3. 테스트 먼저

이슈의 **완료 조건**과 **작업 내용**을 테스트 목록으로 바꾼다. 테스트 하나가 완료 조건 하나 이상을 증명해야 하고, 증명하지 못하는 완료 조건(실서비스 확인, 운영 데이터 조회 등)은 "확인하지 못한 것"으로 따로 적어 둔다.

- 테스트 위치·이름·헬퍼는 저장소의 기존 테스트를 따른다(새 테스트 프레임워크를 들이지 않는다).
- 외부 서비스·실계정이 필요한 테스트는 기본 실행에서 빼고(예: Rust `#[ignore]`), 실행하지 않았으면 실행했다고 쓰지 않는다.
- 테스트만 담은 커밋을 먼저 만들어도 좋다(리뷰어가 "테스트가 무엇을 요구하는지"를 따로 볼 수 있다).

## 4. 구현

- **이슈 범위만** 고친다. 작업 중 발견한 다른 문제(버그, 정리할 코드)는 고치지 말고 메모해 두었다가 끝에 github-issue 스킬로 새 이슈를 만들거나 사용자에게 알린다. 범위가 섞인 PR 은 리뷰와 되돌리기가 어렵다.
- 언어 가이드(CODE_STYLE·CLEAN_ARCHITECTURE)를 따른다. 가이드와 기존 코드가 다르면 **이슈가 다루는 코드만** 가이드에 맞추고, 주변 코드 일괄 수정은 하지 않는다.
- 작업 단위마다 커밋한다. 메시지는 github-pr 스킬 형식(`<type>: <무엇을> (<이슈 ID>)`), 파일은 경로로 추가한다.
- 생성물(예: `.sqlx/`, lock 파일, 스냅샷)이 있는 저장소면 저장소 문서대로 다시 만들어 함께 커밋한다.
- DB 마이그레이션은 저장소 규칙(적용된 파일 수정 금지, 새 파일로 추가 등)을 따르고, 운영 데이터 확인이 필요한 단계는 코드로 대신하지 말고 이슈의 사용자 확인 항목으로 남긴다.

## 5. 검증

1. `verify` 명령 전부(없으면 언어 가이드의 기본 검사 — Rust: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`).
2. 1단계 기준선과 비교 — 새로 실패한 테스트 0, 테스트 수 변화가 의도와 맞는지(종류별 기준은 상세 문서).
3. 완료 조건을 하나씩 대조해 "통과 근거(테스트 이름·명령 출력)" 또는 "확인 못 함(이유)"을 적는다.
4. `git diff <기본 브랜치>...HEAD` 를 처음부터 끝까지 읽는다 — 의도하지 않은 변경, 남은 디버그 코드, 지운 코드를 아직 참조하는 곳(`grep`), 비밀값.

실패하면 고치고 다시 검증한다. 같은 실패를 세 번 넘게 못 풀면 멈추고 시도한 것과 막힌 지점을 사용자에게 알린다.

## 6. 이슈 갱신

- 이슈 본문 "작업 내용"에서 끝낸 항목을 체크한다(`gh issue edit <N> --body-file`). 본문의 결정·검토 항목은 바꾸지 않는다.
- 하지 못한 항목·새로 생긴 사용자 확인 사항은 이슈 댓글로 남긴다.

## 7. PR

github-pr 스킬로 PR 을 만든다(제목 = 이슈 제목, 본문 = 커밋 요약 + 검증 결과 + `Closes #N`). 검증 섹션에 5단계 결과를 그대로 옮기고, 확인하지 못한 완료 조건을 빠짐없이 적는다.

마지막으로 사용자에게 알린다: PR 링크, 확인하지 못한 것, 새로 만든 이슈, 배포 순서 같은 주의점. PR 리뷰는 같은 저장소에서 **다른 세션**으로 pr-reviewer 스킬을 쓰도록 안내한다 — 구현한 세션이 스스로 검토하면 같은 가정을 반복하기 쉽다.
