# 신규 기능·버그 수정

바뀌는 동작이 있는 작업. 테스트가 먼저 그 동작을 요구하고, 구현이 그 테스트를 통과시킨다.

## 테스트 작성

1. 완료 조건마다 테스트 이름을 먼저 정한다 — 이름만 읽어도 무엇을 보장하는지 알 수 있게(예: `order_with_unknown_option_returns_404`).
2. 경계·실패 경로를 함께 쓴다. 성공 경로만 있는 테스트는 리뷰에서 가장 먼저 지적된다:
   - 입력 검증(필수값 누락, 범위 밖, 알 수 없는 값)
   - 권한(다른 사용자·파트너의 리소스, 역할별 접근)
   - 상태 변경의 결과(DB 에 무엇이 남는지), 부분 실패, 재요청(멱등)
   - 외부 응답(성공·오류·응답 없음 — 목 서버로)
   - 버그 수정이면 **버그를 재현하는 테스트**를 맨 먼저
3. API 계약(필드 이름, 상태 코드, 오류 코드)은 응답 본문으로 확인한다 — 내부 함수만 테스트하면 직렬화 실수를 놓친다.

## 실패 확인 (red)

구현 전에 새 테스트를 돌려 **기대한 이유로 실패**하는지 본다(컴파일 오류·404·값 불일치 등). 처음부터 통과하는 테스트는 아무것도 증명하지 못하므로 다시 쓴다 — 이미 구현돼 있었다면 사용자에게 알린다.

## 구현 (green)

- 테스트를 통과시키는 가장 단순한 구현부터. 그다음 가이드에 맞게 정리(enum, 모듈 위치, 오류 분리)하고 다시 돌린다.
- 새 상태·종류 값은 문자열이 아니라 enum 으로(CODE_STYLE §2).
- 새 API·설정·환경변수는 저장소 문서(README, API 명세, `.env.example`)에도 반영한다.

## 검증 기준

- 기준선 대비: 기존 테스트 전부 통과, 새 테스트 수 = 추가한 수.
- 새 테스트를 하나 골라 구현을 잠시 되돌리면 실패하는지 확인할 수 있으면 더 좋다(테스트가 실제로 구현을 검사하는지).
