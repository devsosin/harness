# 작업 후 정리

목표: 작업이 끝났을 때 **이 작업이 만든 것**은 남기지 않고, **다른 사람·세션의 것**은 지우지 않는다. 지우는 판단의 근거는 "누가 만들었나"와 "다시 만들 수 있나" 두 가지다.

| 분류 | 예 | 처리 |
|---|---|---|
| 이 작업이 만든 것 | `-p <id>` 로 띄운 compose 스택, 이 세션의 워크트리, 병합된 이 이슈의 브랜치, 임시 비밀번호 파일 | 바로 정리 |
| 이 작업이 켠 기존 컨테이너 | 멈춰 있던 공유 DB·개발 컨테이너를 이 세션이 `docker start`·`compose up` 으로 켠 것 | 멈춤(지우지 않음) |
| 다른 작업이 남긴 캐시 | 컨테이너 없는 `*_target`·`*cargo-registry`·`*cache` 볼륨, dangling 이미지, 빌드 캐시 | 목록·크기를 보여 주고 확인 후 정리 |
| 데이터 | `*pgdata`·`*-db-data` 등 DB·상태 볼륨, 배포 이미지 태그 | 사용자가 그 이름을 지우라고 할 때만 |
| 쓰는 중 | 세션 시작 전부터 돌던 컨테이너와 그 볼륨 | 건드리지 않음 |

**세션이 쓴 컨테이너는 끝나면 하나도 돌고 있지 않게 한다.** 띄운 것은 지우고, 켠 것은 멈춘다. 세션 전부터 돌던 것만 그대로 둔다. 남겨 둔 컨테이너는 메모리를 잡고(Docker VM 이 모자라면 엔진 전체가 멈춘다) 다음 정리 때 "누가 쓰는 중인지"를 흐린다.

**지워도 되는 근거는 "다시 만들 수 있다"이다.** 컨테이너·캐시는 compose 파일과 띄우는 명령이 남아 있으면 언제든 다시 만들 수 있다. 그래서 지우기 전에 다시 만드는 방법이 기록돼 있는지 본다(3단계). 데이터 볼륨은 compose 로 다시 만들면 빈 DB 가 되므로 이 근거가 통하지 않는다.

다시 만들 수 없는 것을 잘못 지우면 되돌릴 방법이 없다. 그래서 "모르겠다"는 늘 묻는 쪽으로 분류한다. 사용자가 "다른 세션은 끝났다"처럼 범위를 넓혀 주면 4단계의 넓힌 범위 규칙을 따르되, 데이터는 여전히 이름을 대고 묻는다.

## 1. 이 작업이 만든 것 적기

대화와 작업 기록에서 먼저 모은다. 스크립트는 "누가 만들었나"를 모르기 때문이다.

- 백그라운드 작업(셸·모니터·서브에이전트)과, **컨테이너 안에서 돌린 명령**. 호스트의 `docker exec` 를 멈춰도 컨테이너 안 `cargo`·`npm` 은 계속 돌며 빌드 잠금·메모리를 잡는다 — `docker exec <c> pkill -f <명령>` 이나 컨테이너 정지로 끝낸다.
- 띄운 compose 프로젝트 이름(`docker compose -p <이름>`)과 띄운 명령, 따로 만든 컨테이너·이미지.
- **켠** 컨테이너 — 세션 시작 때 멈춰 있었는데 이 세션이 시작한 것. 세션 전부터 돌던 것과 구분해 둔다(정리 때 멈출 대상).
- 만든 git 워크트리, 브랜치, 그 브랜치의 PR 번호.
- 이 작업이 시작한 세션(앱이 세션 도구를 줄 때: `list_sessions` 의 linked 목록).
- 스크래치·임시 폴더에 둔 파일 — 특히 비밀번호·토큰을 적은 파일.

## 2. 현재 상태 보기 (읽기 전용)

```bash
node "${CLAUDE_SKILL_DIR}/scripts/inventory.mjs" --mine <compose 프로젝트>... --repo <저장소>...
```

- git: 워크트리(깨끗한지), 브랜치(기본 브랜치에 병합됐는지, upstream 이 지워졌는지).
- Docker: 컨테이너(MINE 표시, compose 파일이 남아 다시 만들 수 있으면 `recreatable`, 없으면 `compose-files-missing`, 재시작 정책 없는 실행 중 컨테이너), 볼륨 분류(`MINE`·`MINE-DATA`·`CACHE`·`CACHE-ATTACHED`·`DATA`·`IN-USE`·`UNKNOWN`)와 크기, 내 이미지·dangling 이미지, 내 네트워크.
- Windows: `docker_data.vhdx` 크기, Docker 가 실제로 쓰는 양, 압축으로 돌려받을 수 있는 양, 호스트 드라이브 용량·여유와 압축 기준(5단계), 기준을 넘었는지(`PROPOSE`).
- `--json` 이면 같은 내용을 JSON 으로. 스크립트는 아무것도 지우지 않는다.

이름으로 붙인 분류는 추정이다. `CACHE` 라도 이름이 애매하면(`app-data-cache` 등) 데이터로 보고 묻는다.

## 3. 정리 — 이 작업이 만든 것

순서가 있다: 쓰는 쪽을 먼저 멈춰야 그다음 것이 지워진다.

1. **작업·프로세스**: 남은 백그라운드 작업과 컨테이너 안 명령을 멈춘다.
2. **세션**: 이 작업이 시작한 세션이 끝났으면 보관(archive)을 제안한다. 세션은 사용자가 다시 열어 볼 수 있는 기록이라 지우지 않고, 보관도 사용자 확인 후에 한다.
3. **git**
   - 워크트리: 깨끗하면 `git worktree remove <path>`. 커밋 안 된 변경이 있으면 지우지 않고 알린다.
   - 로컬 브랜치: PR 이 병합됐는지 확인한다 — squash·rebase 병합은 `git branch --merged` 에 안 잡히므로 `gh pr view <브랜치> --json state` 로 본다. `MERGED` 이고 지금 체크아웃한 브랜치가 아니면 `git branch -D <브랜치>`. 체크아웃 중이면 기본 브랜치로 옮기고 최신으로 맞춘 뒤 지운다. 작업 트리에 사용자 수정이 있으면 옮기기 전에 알린다.
   - 원격 브랜치: 저장소가 병합 시 자동으로 지우지 않았고 PR 이 병합됐으면 지울지 한 번 묻는다(다른 사람이 볼 수 있는 곳이라).
4. **다시 만드는 방법 확인**: 내 스택을 지우기 전에, 같은 환경을 다시 띄우는 명령이 남아 있는지 본다 — 저장소 `.claude/github-issue.yml` 의 `test_env.setup`, README, 또는 이 작업이 쓴 명령. 저장소에 기록이 없으면 이 작업이 쓴 명령으로 `test_env` 항목을 제안한다(파일을 고칠지는 사용자에게 묻는다). 스크래치 폴더에만 있던 override 파일(`noports.yml` 등)은 내용이 짧으면 그 제안에 함께 적는다. 명령을 몰라도 이 작업의 스택은 지우되, 보고에 "다시 만드는 방법 없음"을 적는다.
5. **켠 컨테이너 멈추기**: 1단계에서 적은 "켠" 컨테이너를 `docker stop <이름>` 으로 멈춘다. 지우지는 않는다(다른 작업의 것이다).
6. **Docker(내 스택)**: 이름을 명시해서 지운다.
   ```bash
   docker compose -p <이름> -f <compose 파일> down -v --rmi local   # 컨테이너·네트워크·볼륨·빌드 이미지
   ```
   compose 파일이 없거나 환경변수가 없어 `down` 이 안 되면 `docker container rm`, `docker volume rm`, `docker image rm`, `docker network rm` 에 이름을 하나씩 준다. `MINE-DATA` 는 이 작업의 임시 DB 일 때만 지운다(대화에서 확인).
7. **임시 파일**: 이 작업이 만든 비밀번호·토큰 파일과 임시 스크립트를 지운다(`down` 에 필요하면 그 뒤에).

`docker system prune -a --volumes` 처럼 범위를 이름으로 정하지 않는 명령은 쓰지 않는다 — 멈춰 있을 뿐인 다른 프로젝트의 DB 까지 지운다.

## 4. 다른 작업이 남긴 것 — 묻고 정리

`CACHE`(쓰는 컨테이너 없음), dangling 이미지, 빌드 캐시를 크기와 함께 한 번에 보여 주고 묻는다. 지울지 정하는 데 필요한 것만: 이름, 크기, 어느 프로젝트(compose 라벨·작업 폴더) 것인지, 지우면 무엇이 느려지는지(다음 빌드가 처음부터).

`DATA`·`UNKNOWN`·배포 이미지 태그는 지우자고 권하지 않는다. 디스크가 정말 부족하면 크기만 알리고, 사용자가 이름을 대면 지운다.

**사용자가 범위를 넓혔을 때**("다른 세션 다 끝났어", "안 쓰는 거 다 정리해"): 다시 만들 수 있는 것은 묻지 않고 지운다.
- `CACHE` 볼륨, dangling 이미지, 빌드 캐시.
- **멈춰 있고 `recreatable` 인** 다른 프로젝트 컨테이너와, 그 컨테이너에만 붙은 `CACHE-ATTACHED` 볼륨. compose 파일이 남아 있어 다음에 `up` 하면 다시 생긴다(빌드는 처음부터).
- `compose-files-missing` 컨테이너는 다시 만들 방법이 없으니 묻는다.
- 실행 중인 컨테이너, `DATA`·`UNKNOWN`·`MINE-DATA`(이 작업 것 제외) 볼륨, 배포 이미지 태그는 넓힌 범위에서도 지우지 않는다.

## 5. WSL 디스크 압축 (Windows Docker Desktop)

`docker_data.vhdx` 는 커지기만 한다. 볼륨을 지워도 Docker 안의 빈 공간이 될 뿐 Windows 디스크는 돌아오지 않는다.

- **기준은 호스트 디스크 크기에 맞춘다**: 압축하는 동안 모든 컨테이너가 멈추므로, 디스크에서 의미 있는 만큼 돌려받을 때만 할 가치가 있다. 드라이브 용량 256GB 이하는 회수 예상 20GB, 512GB 이하는 50GB, 그보다 크면 용량의 10%. inventory 가 이 기준과 `PROPOSE` 여부를 계산해 보여 준다. 정리로 지울 양이 있으면 그만큼 더해 다시 판단한다(지운 뒤 inventory 를 다시 돌리면 정확하다).
- 기준을 넘으면 제안하고, 못 넘으면 수치만 보고한다. 단, 드라이브 여유가 10% 아래이거나 사용자가 "디스크 줄여줘"처럼 직접 요청했으면 기준과 관계없이 진행 계획을 세운다.
- 제안할 때 알릴 것: 회수 예상량, **실행 중인 모든 컨테이너가 몇 분 멈춘다**는 것(목록 — 3단계에서 멈춘 것은 빠진다), UAC 창에서 "예"를 눌러야 한다는 것. 압축은 3·4단계 정리가 끝난 뒤에 한다.
- 사용자가 동의하면:
  ```powershell
  powershell -NoProfile -ExecutionPolicy Bypass -File "${CLAUDE_SKILL_DIR}/scripts/compact-vhdx.ps1"
  ```
  `-DryRun` 은 대상과 멈출 컨테이너만 보여 준다. 스크립트는 fstrim → Docker Desktop 종료 → `wsl --shutdown` → `diskpart compact vdisk`(UAC) → Docker Desktop 시작 → 재시작 정책이 없어 안 돌아온 컨테이너 다시 시작 → 전후 크기 출력 순으로 한다. 몇 분 걸리므로 백그라운드로 돌리고 끝나면 결과를 읽는다.
- 끝나면 2단계 스크립트를 다시 돌려 컨테이너가 전과 같이 떠 있는지 확인한다.

Docker 엔진이 응답하지 않을 때(`docker ps` 가 멈춤·500 오류) 메모리 부족인 경우가 많다. `%USERPROFILE%\.wslconfig` 의 `memory` 를 확인해 알리고, 그 파일을 고칠지는 사용자가 정한다(시스템 설정이다).

## 6. 보고

마지막에 세 묶음으로 짧게 알린다.

- **지운 것**: 종류별 이름과 되찾은 크기(Docker `system df` 전후, vhdx 전후, C: 여유 공간).
- **남긴 것과 이유**: 데이터 볼륨, 다른 프로젝트 스택, 커밋 안 된 워크트리 등.
- **물어볼 것**: 4단계 목록, 원격 브랜치, 세션 보관, vhdx 압축 — 아직 답을 못 받은 것만.

지우지 못한 것(권한·잠금·엔진 응답 없음)은 숨기지 않고 무엇이 왜 남았는지 적는다.
